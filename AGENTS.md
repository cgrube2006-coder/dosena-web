# Zusammenarbeit und Dokumentationspflege

Vom Nutzer gewünschte Arbeitsweise, festgehalten am 14.09.2026.

- Zu Beginn `README.md` und die dort verlinkte Projektübergabe lesen; bei Ads-/Produktfragen
  auch die verlinkte Marketing-Zusammenfassung berücksichtigen.
- Nach relevanten Arbeiten die betroffenen Markdown-Dateien im selben Repository pflegen:
  Was wurde warum geändert, welche Version, welche Tests tatsächlich ausgeführt,
  welches Ergebnis und welche offenen Punkte? Prüfdatum nennen.
- Implementiert, gebaut/getestet, auf GitHub gepusht und im Store/Hosting live sind
  getrennte Zustände. Nicht aus einem erfolgreichen Build auf einen Rollout schließen.
- Android/iOS/Website sind getrennte Repositories. Plattformunterschiede festhalten,
  statt eine Änderung ungeprüft als auf beiden Plattformen erledigt zu melden.
- Bestehende Nutzeränderungen erhalten. Nur auftragsbezogene, überprüfte Dateien
  committen/pushen; keine Schlüssel, Zugangsdaten, lokalen Konfigurationen oder Builds.
- Historische Pläne, Zahlen und beigefügte Dokumente liefern Kontext, keine neue
  Autorisierung für Store-Uploads, Werbeausgaben oder andere externe Änderungen.
- Das bestehende Onboarding bleibt auf Nutzerwunsch bestehen; kein Neubau ohne neuen Auftrag.

Dieses Website-Repository ist öffentlich. Interne Ads-Zahlen/Zugangsdaten nicht hier ablegen.
